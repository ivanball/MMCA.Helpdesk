# CLAUDE.md

Helpdesk-specific guidance. Cross-repo conventions live once in the workspace `../CLAUDE.md`; framework patterns live in `../MMCA.Common/CLAUDE.md` and the ADRs. Do not re-derive either here.

## What this repo is

MMCA.Helpdesk is the **runnable reference application** for [MMCA.Common](../MMCA.Common), and the worked companion to the two adoption guides in `../Website/docs-src/guides/`: `common-GETTING-STARTED.md` (the six-step `dotnet new mmca-app` path) and `common-BUILD-BY-HAND.md` (phase by phase, **every phase mapping to real code here**). It is deliberately minimal and monolith-first: one business module (`Tickets`) exercised end to end through all five layers, demonstrating the "build the monolith now, extract a service later" path.

## This repo is ALSO the dotnet-new template source

The `MMCA.Templates` pack (`mmca-app`, `mmca-module`, `mmca-command`, `mmca-query`) is packed from **this tree**, not a copy. `.template.config/` makes the seed itself a template; `build/templates/stage.ps1` is the only mechanical step, dropping repo-only files and laying `build/templates/overlay/` on top.

- **Never create a parallel copy of the solution for the template.** The single-source property is the whole design: the app whose CI keeps it green IS what adopters get.
- **Renaming or moving anything `stage.ps1` anchors on breaks the pack loudly, by design** (it throws rather than shipping a half-staged template). Update the anchors there.
- **The seed's own green CI does NOT prove the template works.** `build-and-test` builds in local-source mode against Common's `main`; a generated app builds in package mode against a release, and local mode can pass where package-mode Release fails on an analyzer. **Run `pwsh build/templates/smoke.ps1` before touching anything under `build/templates/`, `templates/` or `.template.config/`.** It runs three full generate + restore + Release build + test cases (two module shapes, one SOLUTION shape with `--database sqlite --no-aspire`); two go on to add a second module through `build/add-module.ps1`, the first proving the WIRE-UPS and the sqlite case proving the ENGINE reaches the second module.
- **There is deliberately no `dotnet format` post-action.** dotnet new's run-script post action needs `--allow-scripts yes` and otherwise PROMPTS, which would hang `smoke.ps1` and every adopter's automation, and it would run before the app is built. A relaxed staged `.editorconfig` (SA1210/SA1211/IDE0021) plus a README command is the supported answer for using-directive and alias order, the one thing the scaffold does not hand over.
- **The `IntegrationEventContractTests` subclass ships in the seed**, and `build/add-module.ps1` appends the new module's event to `ExpectedContract`, so a second module does not turn the adopter's next test run red.
- **Optional axes are marked in the seed as ordinary comments, never raw `//#if`.** Whole files come out through `sources.modifiers` conditions; partial-file regions use `// template:begin <label>` / `// template:end <label>` (`<!-- -->` in XML and resx, `@* *@` in razor, `///` inside an XML doc block). `stage.ps1` converts them to dotnet-new directives in the STAGED copies and throws on an unbalanced or unknown label. **Keep a region's trailing blank line INSIDE it** (a marker followed by a blank line is SA1512). Module axes: `--flat`, `--no-status`, `--no-description`, `--no-owner`, `--child <Name>`, plus four combination labels.
- **`--database sqlserver|sqlite|postgresql` is a SWAP, not a removal**, and the seed can only hold one branch: it keeps the SQL Server code in a `sqlserver` region and `stage.ps1`'s `$engineAlternatives` table **injects** the SQLite and PostgreSQL branches as sibling regions at staging time. Several alternatives may anchor on the SAME region, each carrying its own label so the anchor stays unique for the next. Everything else is handled by two derived symbols: `engineName` rewrites `SqlServer`, `engineNameUpper` rewrites `SQLServer` (PostgreSQL is the one choice where both take the same value).
  - **Two package ids the rename cannot reach** are why the `sqlserverOrSqlite` label exists: `Microsoft.EntityFrameworkCore.SqlServer` and `AspNetCore.HealthChecks.SqlServer` rename cleanly for sqlite but produce non-existent packages for postgresql. `Aspire.Hosting.SqlServer` is deliberately NOT in that set: it renames to the real `Aspire.Hosting.PostgreSQL`.
  - **`.slnx` carries markers** (XML comment form), which is how `--no-aspire` drops the AppHost's `<Project>` line; the solution parsers keep comments.
  - **Three whole files are variants, not regions** (`appsettings.sqlite.json`, `appsettings.standalone.json`, `README.standalone.md`), shipped by the overlay and renamed into place by `sources.modifiers`; `stage.ps1` guards that both declarations exist for each.
  - `--no-aspire` is mmca-app's alone, so its markers are STRIPPED in the module and slice trees. **`--database` reaches `mmca-module` too** (a module's EF configurations inherit an engine-specific base), so that template declares the same five symbols in its own right. **A condition on an undeclared symbol is silently false**, which is why `stage.ps1` asserts all five declarations.
- **A generated module is never the solution's `Default` data source**, and mmca-module's staged design-time factory is rewritten to say so (`$moduleOnlyRewrites`). The seed's factory names the same connection top level and under its own logical name, so the resolver collapses it onto `Default` and scaffolds the Default-only framework tables into its migrations: right for the FIRST module, wrong for every later one (EF refuses to migrate a model with pending changes, so a second module scaffolded that way stops the host at startup). The other half is in `build/add-module.ps1`: the orchestration host's data-source call is inserted **above** the existing one, because every such call also rewrites the top-level connection string and the last one wins.
- **XML comments cannot contain a double hyphen**, so an option name written as `--no-aspire` inside a `.props` / `.csproj` / `.slnx` comment makes the whole file invalid XML. **MSBuild does not fail on an unparsable OPTIONAL import, it skips it**, which is how the overlay's `local.props` sat broken (every `--local-mmca` app silently built in package mode) with a green smoke run. Spell option names without their dashes in XML prose; `stage.ps1` guard 8 parses every staged XML file.
- **A comma-separated list cannot lose one element to a whole-line region** (C# forbids a trailing comma in an invocation, parameter list or positional record). The seed keeps those lists on ONE line and `stage.ps1`'s `Convert-OptionalAxisLine` rewrites each into one conditional block per combination, deriving every variant by removing the axis's own segment; its `$optionalAxisLines` table throws on a missing file, an unexpected hit count, or a segment that no longer matches. Reshaping the seed is still preferred where it works.
- **`build/add-module.ps1` is `copyOnly`, and its leak check is INVERTED.** Because it ships verbatim (so the flag names it passes through survive), it may use any hazard word in prose, but it must contain **no seed noun at all**: at run time inside a generated app, `MMCA.Helpdesk` / `Helpdesk` / `Ticket` name nothing. It discovers the solution file, existing modules and host/test projects by glob, and performs the seven wire-ups `mmca-module` can only print plus the first EF migration. `smoke.ps1` adds its second module THROUGH this script, so the wire-ups get CI coverage on the code path adopters run.
- **`Comment` is a rename token, so the word is a hazard.** `--child` replaces the substring `comment` everywhere, which is why the seed says "code notes" and "children" in prose, `.editorconfig` is `copyOnly`, and `stage.ps1` escapes the ResX schema's `name="comment"` attribute and greps the staged trees for `commented` / `commenting`.
- `MMCA.Templates` is deliberately **not** `MMCA.Common.Templates`: that prefix carries the ADR-016 lockstep contract and ships from the Common repo. This one ships on its own cadence and pins the framework version as a template parameter. Releasing it is a `templates-vX.Y.Z` tag running `.github/workflows/release-templates.yml`; **that filename is load-bearing** (keyless OIDC trusted publishing pinned to owner + repo + workflow filename, no API-key fallback).

## Build, test, run

This scaffold defaults to **local-source mode**: `local.props` is **committed here** (unlike Store/ADC, where it is gitignored), sets `UseLocalMMCA=true` and points at `../MMCA.Common/Source`, so packages resolve via `ProjectReference` with no token. The swap lives in `Directory.Build.targets`; `nuget.config` lists nuget.org only. To consume published packages instead, just delete `local.props`. **Local-source mode requires `../MMCA.Common/Source` to exist on disk.**

```bash
dotnet build MMCA.Helpdesk.slnx
dotnet test  --solution MMCA.Helpdesk.slnx      # domain + application + architecture, NO database needed
dotnet run --project Source/Hosting/MMCA.Helpdesk.AppHost   # interactive terminal ONLY

dotnet test --project Tests/Modules/Tickets/MMCA.Helpdesk.Tickets.Domain.Tests/MMCA.Helpdesk.Tickets.Domain.Tests.csproj -- --filter-method "*Create_WithEmptyTitle*"

dotnet ef migrations add <Name> \
  --project Source/Hosting/MMCA.Helpdesk.Migrations.SqlServer.Tickets \
  --startup-project Source/Hosting/MMCA.Helpdesk.Migrations.SqlServer.Tickets \
  --context SQLServerDbContext
```

`DesignTimeSQLServerDbContextFactory` never opens a connection for `add`/`script`; `HELPDESK_TICKETS_SQL` overrides the connection string for `apply`.

**Run caveats:**
- The Aspire AppHost **stalls if launched headless**: only run it in an interactive terminal.
- The full POST/GET round-trip needs a reachable SQL Server, which the sandbox has none of. Unit + architecture tests need no DB and do run.
- The dashboard exposes `sql`, `web` (the API) and `ui` (Blazor). Open **`ui`** to use the app. The `web` API serves `GET/POST /Tickets`, `/health`, `/alive`: **no page at `/`, so the API root returns 404 by design.**

## Architecture: how a request flows

The one module, `Tickets`, spans five projects under `Source/Modules/Tickets/` (`Shared`, `Domain`, `Application`, `Infrastructure`, `API`): the canonical layer layout. Hosts live separately: `Source/Hosts/MMCA.Helpdesk.Web` (the API monolith), `Source/Hosts/UI/MMCA.Helpdesk.UI.Web` (Blazor), `Source/Hosting/` (AppHost + migrations). Folder convention follows the workspace rule; **this layout is what `mmca-module` generates, so keep the two in step.**

**The host DI sequence is load-bearing and fixed** (`Web/Program.cs`): `AddApplication()` -> `AddInfrastructure()` -> the three opt-ins on top of it (`AddAuditTrail()` -> `AddScheduledJobs()` -> `AddMultiTenancy()`, order irrelevant among themselves) -> `AddAPI(modulesSettings)` -> `AddErrorResources<TicketsErrorResources>()` (module error-code translations for localized ProblemDetails, ADR-027) -> `ModuleLoader.DiscoverAndRegister(...)` -> `AddBrokerMessaging()` -> **`AddApplicationDecorators()` must come last**.

**Aggregate conventions** (`Domain/Tickets/Ticket.cs`): the patterns the reference app exists to demonstrate.
- Created through a static `Create(...)` **factory returning `Result<Ticket>`**, never a public ctor (enforced by `EntityConventionTests`); invariants live in `TicketInvariants` composed with `Result.Combine`.
- `[IdValueGenerated]` + the `TicketIdentifierType = int` alias means IDs are **database-generated**, so the factory raises **no "Added" domain event** (the id is still 0); creation is signalled *after commit* by `CreateTicketHandler` publishing `TicketOpenedIntegrationEvent` with the real id. A `TicketTests` case asserts `DomainEvents` is empty after `Create`: **do not "fix" it.**
- Mutations raise a `TicketChanged` **domain event**, dispatched in-process after `SaveChangesAsync` within the same transaction. `Delete()` cascade-soft-deletes children.

**The caching pair is wired, not just available:** `GetTicketByIdQuery` implements `IQueryCacheable` and every ticket command implements `ICacheInvalidating`, both keyed through `TicketCacheKeys`. **The decorator matches the two by string prefix, so a read key that drifts out of `TicketCacheKeys.Prefix` goes stale silently**; `TicketCacheInvalidationTests` is what catches that. Keep both halves pointing at `TicketCacheKeys`.

**Two event paths, deliberately distinct:** *domain events* are intra-module, dispatched synchronously post-save; *integration events* go through the outbox (`IEventBus.PublishAsync`): in-process in the monolith, over a broker once Tickets is extracted, with no handler change (ADR-003 / ADR-008). Integration events carry a `SchemaVersion` (ADR-010).

**Use cases / wiring:** handlers are **convention-scanned by Scrutor** via `ScanModuleApplicationServices<ClassReference>()`; you do not register each by hand. The plain-CRUD write side is the framework's own: one `AddEntityCrud<Ticket, ...>()` call closes the generic create/update/delete handlers over the module's types, the mutation stays on the aggregate behind `TicketUpdateApplier`, and the controller constructs `UpdateEntityCommand<...>` directly. **Three ordering facts are load-bearing and silent**: `AddEntityCrud` runs AFTER the scan (it uses `TryAdd`, so `CreateTicketHandler` keeps the create verb and `TicketUpdateHandler`, which exists only to eager-load the children the response carries, keeps the update verb); the same call registers the `CommandRequestValidator` bridge for the closed framework command (the scan's own bridge only sees commands declared in the module assembly, so without it `TicketUpdateRequestValidator` would silently stop running); and `DeleteTicketHandler` stays hand-written with its own command, because it loads the children so `Delete()` can cascade and because it is the source of the `mmca-command` slice template. `TicketsCrudRegistrationTests` pins all of it. Read endpoints come from `EntityControllerBase`; writes inject handlers into `TicketsController`. Mapping is manual via Mapperly source generators, not AutoMapper (ADR-001).

**Filtered indexes are engine-aware, never a SQL literal.** `TicketConfiguration` uses `HasSoftDeleteFilter(DataSource.SQLServer)` rather than `HasFilter("[IsDeleted] = 0")`. The engine token is the one `engineNameUpper` renames, so a `--database postgresql` scaffold gets `"IsDeleted" = false`; PostgreSQL rejects both the brackets and the comparison with `0` at `CREATE INDEX`. On SQL Server the produced string is byte-identical to the old literal, so the checked-in migrations are unchanged. **Copy this, not a literal, for any new filtered index.**

**Persistence:** `ModuleApplicationDbContext` is abstract and only declares the module's `DbSet`s; the concrete runtime context is the single `SQLServerDbContext` from MMCA.Common: **one instance per database, never a per-module context class** (ADR-006). EF entity configurations are auto-discovered by assembly-name convention, which is why `Infrastructure/DependencyInjection.cs` is a near no-op.

**UI:** Blazor Server + MudBlazor calling the API **server-side** via the typed `HelpdeskApiClient` + Aspire service discovery: no browser CORS, no token. **It throws nothing for a server answer**: every method returns `Result` / `Result<T>`, composed from `ProblemDetailsResultReader` (reads the RFC 9457 body into errors) and `HttpResultExecutor` (turns a connection refused or timeout into a failure too). Only the caller's own `OperationCanceledException` propagates, and `GetTicketAsync` reports a missing ticket as a `NotFound` failure rather than a null. The pages therefore **branch instead of catching**, using `TryGetValue` and `LocalizedErrorMessage` from `MMCA.Common.UI.Common`.

## Multi-tenancy demo (and the other opt-ins)

This seed is the framework's runnable reference for multi-tenancy, so unlike ADC and Store it turns the feature on. `Ticket` and `TicketComment` implement `ITenantEntity`, which is the whole domain-side change: the framework adds a required `varchar(64)` `TenantId` column plus an index and composes a named `Tenant` query filter with the existing `SoftDelete` one. `Ticket` also implements `IAuditedEntity`; `TicketComment` deliberately does not, because the trail records history per aggregate.

**Two tenants, because there are two isolation modes**: `acme` has no data-source override, so it shares the pooled database and is separated only by the query filter; `globex` overrides the connection string and lands in its own `Helpdesk_Globex` database. The host migrates it at startup in the per-tenant pass, and the outbox drains per `(source, tenant)` pair.

Two details that look wrong until you know them:

- **The override key is `Default`, not `Tickets`.** Per-tenant overrides are keyed by **physical** source name, and the AppHost injects the same connection string as both the `Tickets` logical source and the top-level one, so the resolver collapses `Tickets` onto `Default`. Keying the override `Tickets` fails `ValidateOnStart` with "overrides a SQLServer data source that does not exist". The design-time factory mirrors that collapse for the same reason: `ScheduledJobs` is a Default-only table, so a factory whose physical source is not `Default` scaffolds a migration without it.
- **`RequireTenant` is `false` here, against the framework default of `true`.** This seed runs issuer-less, so no request carries a `tenant_id` claim and fail-closed would answer every unheadered call, including health probes and the guides' first `curl`, with a 400. `false` makes an unresolved caller the **system** caller, which reads across all tenants. **Any app with a real issuer should delete the line and take the fail-closed default.** The trade-off is not free: an unresolved caller can read every tenant's rows, and a **write** with no tenant resolved throws `CrossTenantWriteException` rather than inserting an untenanted row. That is why the Blazor UI stamps the header rather than relying on the permissive default.

Resolution is claim first, then the `X-Tenant-Id` header, so the same `curl` with `acme` and with `globex` hits two different databases through one code path. The UI host sends the header from `Api:TenantId` (default `acme`). **Adopting on existing data**: the migration adds `TenantId` with a `""` default, which matches no tenant, so pre-existing rows become invisible to every tenant while staying visible to the system caller. A real app stamps those rows before turning `RequireTenant` on.

The other two opt-ins are configuration only. `AuditTrail:Enabled` and `Scheduler:Enabled` travel together (`AddAuditTrail` registers the `audit-trail-cleanup` retention job, but only the scheduler runner runs it). Both are mirrored by `EnableAuditTrail` / `EnableScheduler` on the design-time factory, and **those flags must stay in step with the host settings** or the scaffolded model drifts from the running one.

## Seed-specific gotchas

- **Issuer-less auth by default.** No Identity module ships here, so `Web/Program.cs` registers a bare auth scheme when `Authentication:JwtBearer:Authority` is unset and `TicketsController` is `[AllowAnonymous]`. To add real RS256/JWKS auth: add the Identity module (BUILD-BY-HAND Phase 8), set the authority, and flip the controller back to `[Authorize]`. **Do not add `[Authorize]` without an issuer** or the pipeline rejects every request.
- **Extraction is host-only.** Turning Tickets into its own service changes only the hosting/AppHost (per-service DB, broker, YARP gateway, JWKS): the Domain/Application/Shared/Infrastructure/API code does **not** change. Preserve that property.
- **Architecture fitness functions are real tests.** `Tests/Architecture/` subclasses the shared NetArchTest bases parameterized by `HelpdeskArchitectureMap` (ADR-015). A new module or layer assembly must be registered in that map or the layering rules silently stop covering it.

## Contribution Flow (PR-based)

`main` is server-protected: branch off an up-to-date `main`, PR, green checks, squash-merge. Documentation-only changes included, this file too. Merges here are not deploys.

- **Commit messages use Scoped Commits** (`<scope>: <description>`), not Conventional Commits.
- **The one required check is `build-and-test`** (Release build + headless domain/architecture tests). Two advisory jobs sit beside it: `template-smoke` (the real gate on template changes) and the PostgreSQL canary (`build/templates/canary-postgresql.ps1`: generate with `--database postgresql`, build and test in package mode, scaffold the first migration and apply it to a `postgres:17` service container). The canary is `continue-on-error` and gated on a `changes` job so a docs-only PR never starts the container; that apply step is the only place the SQL the framework emits for PostgreSQL is executed, making it the consumer half of ADR-113. Without `-ConnectionString` the script stops after scaffolding, so it runs on a workstation with no server.
- **CI builds against `ivanball/MMCA.Common@main` as a sibling** in local-source mode, so a change merged to Common `main` can break Helpdesk CI with no Helpdesk-side change. If CI goes red on an untouched area, diff recent Common commits first.
- Helpdesk keeps no `packages.lock.json` files; framework bumps arrive as `Bump MMCA.Common to vX.Y.Z` PRs cut by `/push-release`.

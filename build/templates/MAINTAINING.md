# Maintaining the template pack

Maintainer notes for the `MMCA.Templates` pack (`mmca-app`, `mmca-module`, `mmca-command`, `mmca-query`), which `stage.ps1` packs from this repo's own tree. Read this before changing anything under `build/templates/`, `templates/` or `.template.config/`, and run `pwsh build/templates/smoke.ps1` before and after. The adopter-facing `README.md` beside this file is the package readme on nuget.org; keep maintainer detail here instead. This file sits under `build/`, which `stage.ps1` never copies, so it does not ship.

## Staging and smoke

- **`smoke.ps1` runs three full generate + restore + Release build + test cases** (two module shapes, one SOLUTION shape with `--database sqlite --no-aspire`); two go on to add a second module through `build/add-module.ps1`, the first proving the WIRE-UPS and the sqlite case proving the ENGINE reaches the second module.
- **There is deliberately no `dotnet format` post-action.** dotnet new's run-script post action needs `--allow-scripts yes` and otherwise PROMPTS, which would hang `smoke.ps1` and every adopter's automation, and it would run before the app is built. A relaxed staged `.editorconfig` (SA1210/SA1211/IDE0021) plus a README command is the supported answer for using-directive and alias order, the one thing the scaffold does not hand over.
- **The `IntegrationEventContractTests` subclass ships in the seed**, and `build/add-module.ps1` appends the new module's event to `ExpectedContract`, so a second module does not turn the adopter's next test run red.

## Optional axes and markers

- **Optional axes are marked in the seed as ordinary comments, never raw `//#if`.** Whole files come out through `sources.modifiers` conditions; partial-file regions use `// template:begin <label>` / `// template:end <label>` (`<!-- -->` in XML and resx, `@* *@` in razor, `///` inside an XML doc block). `stage.ps1` converts them to dotnet-new directives in the STAGED copies and throws on an unbalanced or unknown label. **Keep a region's trailing blank line INSIDE it** (a marker followed by a blank line is SA1512). Module axes: `--flat`, `--no-status`, `--no-description`, `--no-owner`, `--child <Name>`, plus four combination labels.
- **A comma-separated list cannot lose one element to a whole-line region** (C# forbids a trailing comma in an invocation, parameter list or positional record). The seed keeps those lists on ONE line and `stage.ps1`'s `Convert-OptionalAxisLine` rewrites each into one conditional block per combination, deriving every variant by removing the axis's own segment; its `$optionalAxisLines` table throws on a missing file, an unexpected hit count, or a segment that no longer matches. Reshaping the seed is still preferred where it works.
- **XML comments cannot contain a double hyphen**, so an option name written as `--no-aspire` inside a `.props` / `.csproj` / `.slnx` comment makes the whole file invalid XML. **MSBuild does not fail on an unparsable OPTIONAL import, it skips it**, which is how the overlay's `local.props` sat broken (every `--local-mmca` app silently built in package mode) with a green smoke run. Spell option names without their dashes in XML prose; `stage.ps1` guard 8 parses every staged XML file.
- **`Comment` is a rename token, so the word is a hazard.** `--child` replaces the substring `comment` everywhere, which is why the seed says "code notes" and "children" in prose, `.editorconfig` is `copyOnly`, and `stage.ps1` escapes the ResX schema's `name="comment"` attribute and greps the staged trees for `commented` / `commenting`.

## The database engine swap

- **`--database sqlserver|sqlite|postgresql` is a SWAP, not a removal**, and the seed can only hold one branch: it keeps the SQL Server code in a `sqlserver` region and `stage.ps1`'s `$engineAlternatives` table **injects** the SQLite and PostgreSQL branches as sibling regions at staging time. Several alternatives may anchor on the SAME region, each carrying its own label so the anchor stays unique for the next. Everything else is handled by two derived symbols: `engineName` rewrites `SqlServer`, `engineNameUpper` rewrites `SQLServer` (PostgreSQL is the one choice where both take the same value).
  - **Two package ids the rename cannot reach** are why the `sqlserverOrSqlite` label exists: `Microsoft.EntityFrameworkCore.SqlServer` and `AspNetCore.HealthChecks.SqlServer` rename cleanly for sqlite but produce non-existent packages for postgresql. `Aspire.Hosting.SqlServer` is deliberately NOT in that set: it renames to the real `Aspire.Hosting.PostgreSQL`.
  - **`.slnx` carries markers** (XML comment form), which is how `--no-aspire` drops the AppHost's `<Project>` line; the solution parsers keep comments.
  - **Three whole files are variants, not regions** (`appsettings.sqlite.json`, `appsettings.standalone.json`, `README.standalone.md`), shipped by the overlay and renamed into place by `sources.modifiers`; `stage.ps1` guards that both declarations exist for each.
  - `--no-aspire` is mmca-app's alone, so its markers are STRIPPED in the module and slice trees. **`--database` reaches `mmca-module` too** (a module's EF configurations inherit an engine-specific base), so that template declares the same five symbols in its own right. **A condition on an undeclared symbol is silently false**, which is why `stage.ps1` asserts all five declarations.
- **A generated module is never the solution's `Default` data source**, and mmca-module's staged design-time factory is rewritten to say so (`$moduleOnlyRewrites`). The seed's factory names the same connection top level and under its own logical name, so the resolver collapses it onto `Default` and scaffolds the Default-only framework tables into its migrations: right for the FIRST module, wrong for every later one (EF refuses to migrate a model with pending changes, so a second module scaffolded that way stops the host at startup). The other half is the orchestration host: `With{Engine}DataSource` sets only the module's own `DataSources` entry, never the top-level connection string, so the AppHost pins that string to the FIRST module with an explicit `ConnectionStrings__<Engine>ConnectionString` override (seed `Program.cs` plus the two `stage.ps1` engine alternatives), and `build/add-module.ps1` routes every later module without touching it. **Without that override the appsettings `localhost` value survives under Aspire**: the readiness check and the `Default` source miss the container and `web` never turns healthy.

## `build/add-module.ps1` and `mmca-command`

- **`build/add-module.ps1` is `copyOnly`, and its leak check is INVERTED.** Because it ships verbatim (so the flag names it passes through survive), it may use any hazard word in prose, but it must contain **no seed noun at all**: at run time inside a generated app, `MMCA.Helpdesk` / `Helpdesk` / `Ticket` name nothing. It discovers the solution file, existing modules and host/test projects by glob, and performs the seven wire-ups `mmca-module` can only print plus the first EF migration. `smoke.ps1` adds its second module THROUGH this script, so the wire-ups get CI coverage on the code path adopters run.
- **`mmca-command` ships a cache-invalidation test builder with every command it scaffolds**, staged from `Tests/.../Tickets/UseCases/Delete/DeleteTicketCommandCacheBuilder.cs` and written by the template's second source seven levels up from the slice folder (the solution root), so a generated slice is green on arrival only when it is generated from the module's `<Module>/UseCases` folder, as `smoke.ps1` does.

## Releasing

`MMCA.Templates` is deliberately **not** `MMCA.Common.Templates`: that prefix carries the ADR-016 lockstep contract and ships from the Common repo. This one ships on its own cadence and pins the framework version as a template parameter. Releasing it is a `templates-vX.Y.Z` tag running `.github/workflows/release-templates.yml`; **that filename is load-bearing** (keyless OIDC trusted publishing pinned to owner + repo + workflow filename, no API-key fallback).
